# 自助补额度与异常审批

## 流程
用户提交原请求标识，服务端重新查询原消费并计算金额，不接受客户端金额、审批状态或自动分流指令。符合规则的消费经二次查询比对、账号核验、事务预占后返还；不满足自动条件但符合申请资格的记录进入待审核。管理员手动申请和旧待审核记录不自动补发。

## 正常自助条件
- 本人、已扣费、输出 token 为零，且满足模型、渠道、用户组、有效期及消费范围限制。
- 上游明确标记 `gemini_empty_candidates` 或 `empty_response`，明确 `billing_source=wallet`。
- 无工具调用、多模态或推理输出、已退款或退款状态不明的标记。
- 已过结算等待期；默认 60 秒，允许配置 30–86400 秒。
- 原消费不超过自助单笔上限，默认 100000 整数 quota；仍受原始和最新补偿比例、单笔上限、个人/全站每日额度与次数约束。
- 申请、自助与执行开关开启，处于开放时段。二次核验时重新检查最新规则和原始规则更严限制。

## 异常与重试
缺少证据、特殊输出、疑似已退款、金额超自助阈值、未完成结算等待或二次核验变化：进入待审核并记录原因。白名单不符、他人消费、订阅、超出有效期或当日额度不足等不合申请资格的情况仍拒绝，不通过审批绕过硬限制。

返还请求超时或成功后落库失败：状态为 unknown，保留额度/次数预占，重复提交只返回已有状态。原站明确拒绝则记 failed，由站长核查。重复原请求及并发提交不会创建第二条申请或重发额度；重启沿用 executing→unknown 的恢复策略。

## 边界
自动判定以受信的管理日志为依据；60 秒等待不是结算完成的数学保证。上线时需保证日志已反映最终扣费与有效输出。当前上游额度接口没有请求级幂等键，因此不自动重试结果不明的转账。去重覆盖本系统记录，不能识别其他后台未写回原日志的人工返还；需要统一返还入口或同步退款标记。订阅消费仍不转换成余额。

自助模式默认开启，但申请、执行、白名单及每日限额仍默认关闭/为空；已有配置通过默认字段兼容。新增批次功能在启动时自动添加可空 `claims.run_id` 列和索引；旧记录独立展示，不推测历史批次，已有申请不会因升级而自动执行。

## 前端
进入补额度页先显示当前账号、累计补回与成功历史，不自动查询上游消费。点击查询后显示当前页可申请额度、模型与笔数，并默认勾选可申请记录。服务端仍逐笔重验资格和金额，批量确认显示预计分流；用户说明选填，人工核验执行仍要求依据。确认前不发放，返回结果逐笔显示成功/待审核/失败/待确认。可能执行返还的请求响应丢失时禁用原提交按钮，保留输入，先刷新核对。

每次提交的批次标识由服务端生成，创建申请时与消费记录同事务保存，重复提交不重新关联批次。`GET /api/refund-records` 按当前身份返回成功批次，按批次分页且不拆分明细；批次下按原消费日期与模型汇总。页面时间范围来自该批次成功记录的最早/最晚原消费时间，不声称是上次查询到本次查询的扫描区间。额度继续使用整数 quota，不复制参考站的人民币换算。

数据统计移除站点选择，曲线来自当前账号的成功账本；鼠标、触摸、方向键、日期滑块均可定位日期并显示额度及成功笔数。没有成功数据时显示零值序列，不填充虚构历史。请求进度条、查询和提交旋转指示、加载及内容出现动画覆盖等待状态；减少动态效果偏好下使用静态指示。
