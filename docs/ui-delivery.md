# 通知中心与界面更新

## 空回查询及时性

用户点击“查询空回”“重新查询”或在查询结果页点击刷新时，调用 `GET /api/logs?refresh=1&view=eligible`。服务端在请求进入查询模块时固定截止时间，精确到秒；首次从管理员允许的最早时间查询，之后从本用户上次成功截止的下一秒接续至本次截止，并受管理员查询天数限制。同秒重复点击不请求上游；同用户并发按先后串行，较晚点击只查询剩余尾段。取消十五秒复用、五分钟重叠、十五分钟回扫和强制全量刷新。

每次拉取固定区间的全部消费页，覆盖所有模型，不接受用户展示条件作为同步范围。取完所有页才把已发现日志和成功截止作为同一条 SQLite 记录原子保存到 `log_query_progress`，空结果也推进。上游失败、空缺页、重复页、总数变化、单次或保留结果超过一万条、落库失败均不推进，明确报错后重试原区间。超过上限需管理员缩短允许查询天数，不静默截断。

用户查询页已移除“筛选条件”区域，固定展示符合规则的记录。翻页仅读取持久结果，不再向上游查询；已发现、仍在有效期内且未补偿的日志继续保留。服务端按当前规则重新检测完整结果后分页，成功项和排除模型在分页前移除，申请与发放仍重新核验原始日志。原始消费管理页的筛选不变。

每次查询会生成一个补偿批次，覆盖本次查询发现的多个模型和多条消费。用户提交后先逐条完成规则/AI 判断；存在待人工记录时整批暂停，全部审核结束后只对通过部分向原站合并加额度一次，并按一次补偿计数。整批会显示记录数、模型数、预计/实际补回额度、审核进度和失败原因；到账不明时整批冻结并只允许整批对账。单次补偿总额可由站长设置，超限、额度不足或规则变化不会静默拆分。

查询进度跨刷新、登出及服务重启保留，独立于可清理缓存。旧的按筛选缓存不能证明全模型完整覆盖，因此不迁移为成功截止；升级后首次查询重新扫描管理员允许区间，已有申请及补偿唯一性校验不变。管理员扩大查询天数不补扫过去已跳过的时间。

界面显示成功截止、本次扫描区间、新发现的消费笔数。按已确认方案，已覆盖时间永不回扫：原站之后才写入、但消费时间属于已覆盖区间的日志不会再被发现。截止仅证明当时可见日志已拉取完成，不保证原站没有延迟入库。

## 管理界面

操作记录采用中文时间线，直接展示动作、结果摘要、关联模型、申请用户、操作人和时间，支持打开关联申请。补偿成功展示实际金额，AI 判定展示结论、置信度和原因，驳回或失败展示处理说明；配置修改显示变更摘要。顶部数量仅统计最近一百条事件，不代表申请总数或实时待办。英文动作、申请编号、原请求标识及完整详情保留在“原始记录”，异常 JSON 不阻断页面。浅色、暗色和移动端共用可读布局。

站长管理的“通知中心”包含钉钉和邮箱两个页签。切换页签保留当前输入，保存后读取服务端结果。邮箱页支持 SMTP 服务器、端口、STARTTLS 或 SSL/TLS、账号、密码、发件邮箱和发件人名称；密码不回显，留空保持原值。保存后才能发送测试邮件，测试邮箱必须单独填写。测试不群发给用户。

邮件的审核通过、补偿成功、补偿失败、结果待确认事件独立控制。通过审核只表示等待执行，不写成已经到账。默认关闭邮箱通知。正式邮件读取 云中猫API小站 用户 `setting.notification_email`，不回退到账号 `email`；无有效通知邮箱显示“已跳过”。同一处理内相同用户、相同事件的多笔申请合并发送；申请与事件组合在数据库中去重，重叠批次不会再发送已入队的申请。

邮件和钉钉均显示中文发送状态、尝试次数与处理结果。邮件最多自动尝试五次，关闭事件会取消未发送的对应队列。SMTP 连接、认证和发送设置超时；错误信息不回显密钥。SMTP 接受邮件不等同于最终送达。SMTP 不提供事务性“恰好一次”投递保证；进程在邮件服务器接受后、写入本地结果前中断，仍可能产生重复邮件，固定 Message-ID 只用于辅助识别。

钉钉的会话预览标题与正文标题一致，按事件及实际状态区分“申请待审核”“审核通过 · 待补偿”“审核已驳回”“补偿成功”“补偿失败”“结果待确认”和 AI 审核结果。同用户同批多模型仍合并一条消息；混合结果在标题列出各状态的笔数，例如“补偿失败 1 / 待审核 1 / 补偿成功 2（4 笔）”。经过 AI 分析的批次增加“AI 审核”前缀。通知中心发送记录展示实际通知标题。旧的纯文本待发送消息按其事件补充标题；已发送通知不重新投递。

SMTP 配置和收件地址加密保存在本工具的数据目录，保留 `secrets.key` 与数据库。发送在后台执行，不阻塞审核与补偿请求。入队异常记录到操作日志，管理员可据此发现异常；不自动重放补偿。测试覆盖模拟投递，不代表已验证真实邮箱服务。

邮箱事件包含审核未通过，邮件正文列出管理员填写的审核意见，并按用户合并同一批多模型申请。

管理员 AI 二次复核独立核对日志、规则和初始判定，提供综合判断、审核建议、原因及证据。只有建议通过、空回判定成立且置信度达到规则阈值时显示“采纳建议并通过补额度”；服务端重新核验日志、规则和限额后执行。订阅消费保留逐笔金额核验流程。AI 建议不自动驳回，也不代替管理员决策。

## AI 阈值与站内通知

AI 开关、自动通过置信度与每日次数修改后在离开输入框时自动保存，并显示服务端确认的阈值。置信度阈值不是模型准确率；开启 AI 后，只有成功完成、判为空回且达到当前阈值的结果允许自动补偿，旧空回标记不能绕过门槛。关闭 AI 后继续使用原规则。保存采用规则版本校验，执行前重新读取当前规则；历史申请不因修改阈值自动重放。

用户通过顶栏铃铛或个人中心“站内通知”查看申请待审核、审核通过、审核未通过、补偿成功、失败及待核对结果，支持仅看未读、单条已读、全部已读与查看申请详情。审核通过与确认到账分别显示。通知和已读状态保存在 SQLite，独立于邮件及钉钉开关；旧库首次升级回填每笔已有申请的当前状态一次。仅本人可读取和标记通知。

登录后及页面切换时读取未读数，页面可见且空闲时每 30 秒更新铃铛。全部已读只覆盖已加载快照的通知范围，之后到达的消息保留未读。相同状态重入及重复申请不会重复生成结果通知，重新审核后的新状态变化保留独立记录。

## 缓存与版本

服务启动时按 HTML、CSS 和全部脚本内容计算界面版本，并固定该版本的资源快照。HTML 引用 `/assets/<内容版本>/app.js` 等地址，模块的相对导入自动继承同一版本目录。只有匹配当前内容版本的资源返回一年 `immutable`；旧的无版本资源地址及 HTML 均返回 `no-store`。不存在的资源版本返回不可缓存的 404，避免把新内容缓存到旧地址。HTML 单独变化也会更新版本。

`GET /api/ui-version` 不缓存、无需登录，只返回公开的界面版本。浏览器每分钟及重新进入页面时检查版本；发现更新显示“刷新到新版”，不强制重载。正在发送请求时禁止通过提示刷新；存在输入或弹窗时先确认。登录页与工作台都显示更新提示，工作台页脚显示当前界面版本。断网不弹出重复报错。

## 部署

Docker 构建通过 `npm ci` 使用提交的 `package-lock.json` 安装生产依赖，然后运行测试。源码直接运行须先执行 `npm ci --omit=dev`。界面与服务端必须作为同一镜像或同一发布目录更新并重启服务。

反向代理/CDN 必须对 `/`、`/?ui=...` 和 `/api/*` 绕过缓存，并遵循源站 Cache-Control。仅对 `/assets/*` 成功响应启用长期缓存。取消覆盖源站响应头的“缓存所有内容”规则；负载均衡发布期间须避免同一用户的 HTML 和资源请求落到不同版本实例。当前 SQLite 架构本身也不支持多个实例共享数据卷。

首次上线此修复时，清除 CDN 中已有的 HTML、`/app.js`、`/style.css`、`/glass.css`、`/icons.js` 及旧模块缓存。已经打开的旧版本如果没有版本检测逻辑，需要重新打开页面或强制刷新一次；新服务无法修改已经存入浏览器的旧脚本。之后使用版本资源与更新提示。不要为解决界面缓存而清理申请、账本、用户会话或业务数据库。

在开发者工具 Network 中核对：HTML 与版本接口为 `no-store`，页面入口资源都带同一 `/assets/<版本>/`，无版本脚本不是 `immutable`，页脚版本与接口版本一致。真实代理的缓存规则仍须在部署环境验证。
